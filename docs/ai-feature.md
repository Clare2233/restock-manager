# AI 自然语言录入（PRD）

> 状态：功能已完整跑通（第四批次真机验收通过），本文在第五批次补齐正文。
>
> 范围：`src/services/ai/`（`deepseek.ts` 网络层 / `prompt.ts` 提示词 / `parse.ts` 解析编排 / `match.ts` 物品匹配）
> 相关：`src/hooks/use-ai-entry.ts` 状态机、`src/components/ai/` UI、首页输入框挂载处 `src/app/(tabs)/index.tsx`
>
> 一句话：**用自然语言记录消耗品流水，降低录入摩擦** —— 打一句「用了一卷纸」等于填完一整张表单。

---

## 1. 产品定位

用户在家的真实行为是「**用完 / 买回来**」，而不是「打开 App 填一张流水表单」。
现有的录入路径（物品列表 → 进详情页 → 点消耗 → 选数量 → 确认）是 4 步，
而用户脑子里那一瞬间想到的话只有一句。

AI 录入要做的事是把这 4 步压缩成 1 步：

- **输入是一句话**，不是一张表单；
- **输出必须由用户确认**，不是静默写库（见决策 1）；
- **失败不阻塞**，任何时候都能退回原有的手动录入路径。

它不是一个聊天机器人，是**一个套了自然语言外壳的表单** —— 这个定位决定了后面所有取舍：
宁愿多一次确认，也不要一句「痛快」写错流水。

---

## 2. 用户场景

| 场景 | 现在的摩擦 | AI 录入带来的变化 |
|---|---|---|
| **高频录入**：每次用完、每次买回来 | 录一条要进详情页、点按钮、切数字键盘；日均几条时会明显嫌烦 | 首页输入框打一句话，确认一次就写完 |
| **手不离物**：正在厨房 / 手上拿着东西 | 不方便双手操作、不方便点屏幕 | 一次输入 + 一次点确认，中间不用找物品在哪 |

两个场景共同的前提是**录入动作要足够短**。一旦它变慢（比如还要多选一次单位），
用户会退回「先不记，晚上一起补」 —— 而补记的那批数据通常已经记不准了。

**不覆盖的场景**（刻意没做）：
离线录入（要联网调 LLM）、批量补录（一句话一条流水，多条要多次输入）、
以及设备端识别（拍照 / 语音输入目前不在范围内）。

## 3. 工作流

```
用户在首页输入框打一句话
  │  AiInputBar（src/components/ai/ai-input-bar.tsx）
  ▼
use-ai-entry.submit()                       ← 整个流程的状态机
  │
  ├─ ① LLM 解析            parseUtterance()
  │     prompt.ts     buildMessages()：system 规则 + 「用户原话 + 已登记物品 name/unit」
  │     deepseek.ts   POST /chat/completions，response_format = json_object，temperature = 0
  │     parse.ts      validate()：action 枚举 / itemName 非空 / quantity 取值域 / confidence 区间
  │                   collectReviewReasons()：要不要让用户复核
  │
  │     └─ 失败 → AiParseFailure(code, message)，**流程到此为止**，不再往下走
  │
  ├─ ② 本地匹配            match.ts（不发网络请求）
  │     matchItem()       exact / candidates / none
  │     checkUnitMatch()  same / converted / review
  │
  ├─ ③ 用户确认            AiConfirmCard（Modal）
  │     把「物品 / 动作 / 数量 / 单位」四项摊开给用户看
  │     可改：数量、价格；可换：物品（候选列表 / 「换一个」/ 「去新建」）
  │     单位对不上 → 黄色提示条（不阻断）；库存要扣穿 → 红色提示条（禁用确认键）
  │
  │     └─ 此时**一个字节都没写进库**
  │
  └─ ④ 写库                itemsStore.recordAiMovement({ itemId, action, quantity, price })
        写之前再算一遍库存是否会被扣穿（UI 之外的数据层兜底）
        流水落 stock_movements，source = 'ai'（决策 8）
```

几个刻意的断点：

- **①② 之间不过滤任何东西**：`itemName` 原样往下传，匹配是独立的一步。
  出现「模型猜的名字和库里不一致」时，能一眼看出是模型的问题还是匹配的问题。
- **③ 是唯一的用户决策点**：所有兜底信号（置信度低、数量缺失、单位不一致、库存不足）
  都汇总到这张卡片上，而不是散布在各层各自弹窗。
- **④ 之前用户可以随时取消**：取消就是什么都不做，不存在「半成品流水」。

## 4. 三层防护

防护的意思是：**LLM 的输出在到达数据库之前，要过三道彼此独立的检查。**
这三层不是冗余 —— 真机上「手帕纸还剩 0 包」卡住那次，**三层各错了一点**，任何一层单独修好都不足以让功能恢复：

| 层 | 文件 | 保护的是什么 | 具体手段 |
|---|---|---|---|
| ① Prompt | `prompt.ts` | 让模型**尽量输出对的东西** | 角色先行 + 「只输出 JSON」说两遍；规则编号列表；few-shot 正例 6 条 + 1 条 negative case；`response_format: json_object` + `max_tokens: 300` |
| ② 形状收窄 | `deepseek.ts` | 类型系统成立 —— 拿到的一定是合法的 `AiParseResult` | `action` 不认识 → 降级 `unknown`；`toQuantity` **按 action 分**（`adjust` 允许 0，其余必须正数）；`toConfidence` 夹到 0~1，非数字按 0 |
| ③ 语义校验 | `parse.ts` | 业务上可用 —— 这条结果能不能拿去生成确认卡片 | `validate()` 再挡一遍取值域；`normalizeUnit()` 保守归一；`collectReviewReasons()` 决定要不要交给用户复核 |

**「三层各错一点」的那次事故**（第五批次复盘写下来，避免重演）：

```
输入「手帕纸还剩 0 包」
  ① Prompt 写死「quantity 只给正数」      → 模型不敢给 0，改给 null
  ② toQuantity 用 toPositiveNumber 收窄   → 就算模型给了 0 也会被吞成 null
  ③ quantity === null 判成「没说清数量」  → 要求用户补一个他**已经说了**的数量

用户看到的：输入被拦住，提示「没说清数量，请补一个」。
三次判断单独看都「有点道理」，合起来把一句合法输入判死了。
```

所以规则是：**某一层偷偷替用户做决定时，另外两层看得见吗？** —— 上面三层当时都不知道对方在兜一次又一次的底。
修完之后，`ai-parse-smoke.mjs` 把「Prompt 说了什么」和「代码怎么收窄」钉在同一个脚本里：任何一层改回去都会红。

## 5. 两条正交防线：置信度阈值 vs 数量缺失

第五批次拿 10 条典型输入问了真实模型（`deepseek-chat`，`temperature = 0`），得到的一个重要结论是：
**拦下模糊输入的其实主要是「数量缺失」检查，不是置信度阈值。**

| 防线 | 拦什么 | 落地位置 | 10 条样本里的表现 |
|---|---|---|---|
| **置信度阈值**（`CONFIDENCE_THRESHOLD = 0.6`） | 拦「**模型自己也虚**」的情况 —— 它对 itemName / action 的把握不够 | `collectReviewReasons` | 只抓到 1 条：「好像用了一些纸」0.5 → `识别把握不高（0.50），请确认` |
| **数量缺失检查**（`quantity === null`） | 拦「**信息本身不全**」—— 用户没给数量，模型也没替他编 | `collectReviewReasons` | 抓到 2 条：「用了一点洗衣液」（0.8）、「好像用了一些纸」（0.5） |

关键点在「用了一点洗衣液」这条：**confidence 高达 0.8**（模型把物品和动作认对了，这个分数是诚实的），
是数量缺失把它拦下来的。**高置信度 ≠ 这条记录信息完整**。

所以：

- 两条防线**正交**：一条看「模型的把握」，一条看「信息齐不齐」，覆盖的是不同维度的含糊；
- **别指望单一机制兜住所有问题** —— 只调阈值挡不住「说得很肯定但没说数量」的输入，
  反过来只查数量也拦不住「都说全了但模型猜错了物品」的输入；
- 也不宜因为「阈值没拦住多少」就删掉它：它抓的是模型层面的犹豫，**触发时机与数量缺失完全不同**
  （一个发生在模型说话的那一刻，一个发生在用户改数量的那一屏），丢掉哪一条都会留一个可穿透的洞。

> 实测分布：`confidence` 出现**双峰 + 中间真空**（信息足够 0.85~0.95 / 缺关键信息 0.5~0.8，0.5~0.85 之间无样本）。
> 因此 0.6 / 0.7 / 0.8 三个值在这批样本上判定完全一致，只有 0.5 会漏。**结论：保留 0.6**，理由见 §7 局限 5。

## 6. 失败兜底（三层）

所有失败走同一个约定：**`parseUtterance` 返回 outcome 对象，不抛异常**；
失败时唯一正确的动作是**退回手动录入**，不存在「失败但也渲染个卡片」的中间态。

| 层 | 触发条件 | 代码信号 | UI 处理 |
|---|---|---|---|
| **轻：需要复核** | 置信度 < 阈值，或 `quantity === null` | `needsReview: true` + `reviewReasons[]` | 卡片**照常出**，复核原因以黄色小字逐条列出来；用户可以当场改数量再确认。**不阻断** |
| **中：匹配不到物品** | `matchItem` → `none`（列表里没有这个物品） | `match.status === 'none'` | 卡片出「没找到『猫罐头』，要不要新建这个物品？」+ **[去新建]**（带着这个名字预填新建表单） |
| **重：解析/调用失败** | Key 缺失、超时、网络、鉴权、HTTP 错误、空响应、JSON 损坏、形状非法、`action === unknown` | `AiParseFailure` + `AiErrorCode` | 首页输入框下方显示一行已脱敏的 `message`，用户原来的输入**保留在输入框里**，可以改完重发，也可以照旧手动录入 |

补充两条同样要拦、但不属于上面三层的事：

- **库存要被扣穿**：不是解析失败，而是「写下去就是错的」。在解析流程之外单独算一次（`resolveStockIssue`），
  出红色提示条并**禁用确认键**，让用户当场把数量改小。
- **失败文案脱敏**：`AiError` 的 message 里可能有 URL 和响应片段，给用户的文案**按 code 分档重写**（`toUserMessage`），
  调试信息只进日志。

## 7. 已知局限

每条都同时回答两个问题：**为什么现在不修**，以及**将来怎么解决**。

### 1. 促销 / 折扣语义识别有限

例如「洗衣液买了两瓶，第二瓶半价」「这一单满 200 减 30」：
prompt 规则 5 只要求 `price` 是**实付总额**，而「实付总额」常常需要用户自己算，
模型勉强算的结果也不值得信 —— 金额错了就是支出统计错了。

- **为什么现在不修**：核心场景（记录消耗）不依赖金额，`purchase` 之外的动作 `price` 恒为 null；
  硬做折扣语义要引入「单价 / 数量 / 优惠」三层字段，而现在物品表单里根本没有单价。
- **将来怎么解决**：金额保持「**让用户手填或留空**」这条默认路径（留空则不记支出）；
  真要支持，先给 movement 加「单价」字段，再考虑在卡片上让用户按行确认金额。现在不做。

### 2. 同类模糊输入的处理风格会摇摆

「用了点东西」→ 模型连「东西」都不肯当物品名，直接 `unrecognized` → 用户看到「没看懂，请手动录入」；
「好像用了一些纸」→ 模型猜成「手帕纸」+ 0.5 → 出一张可以改的卡片。
两种输入都是「没说清」，却落到两条不同的兜底路径上，取决于模型当时敢不敢猜到列表里的某个名字。

- **为什么现在不修**：两条路径都是安全的（都停在人工确认 / 手动录入之前），
  统一它们要改的是 prompt 的「敢猜 vs 不敢猜」策略，而策略上其实还没有答案 ——
  「猜一个让用户改」更省事，「别猜让用户重新说」更诚实。
- **将来怎么解决**：先积累真实样本（哪些话被判 `unrecognized`），再决定偏向哪种风格；
  更稳的方案是把两者合并成一条 —— 出卡片、物品为空、让用户选（相当于把 `unrecognized`
  从「失败」降级成「needsReview 的一种」）。

### 3. 单位换算依赖 `packSize`，目前基本走不到

`checkUnitMatch` 只有「AI 给的单位 == 物品采购单位 且 `packSize > 1`」时才返回 `converted`。
种子数据 `packSize = 1`、`packUnit = null`，所以实际上**任何单位不一致都落到 `review`**（让用户看一眼）。

- **为什么现在不修**：换算能力的开关在**物品数据**里，不在 AI 链路里 —— 物品表单还没引导用户维护采购单位，
  让用户维护之前，服务端推算会悄悄算错。宁可让人看一眼，也不要自动乘错。
- **将来怎么解决**：物品表单支持「采购单位 + 一包多少个」（数据模型已有 `packSize` / `packUnit`），
  用户填过之后 `converted` 自然生效；届时 AI 链路一行都不用改。

### 4. 物品别名（`aliases`）未做

「纸巾」匹配不到「手帕纸」：`match.ts` 第 3 级是**字面子串**匹配，不吃上位词/同义词。
现在靠 prompt 规则 1（要求模型原样抄列表里的名字）缓解，模型抄对了就能过，抄歪了就 `none`。

- **为什么现在不修**：加 `aliases` 要改数据模型 + 迁移，属于「一次说清、长期受益」的事，但不解决眼前的能不能用；
  prompt 规则 1 已经把大部分情况兜住了 —— 10 条样本里 6 条「信息足够」都精确抄对了名字。
- **将来怎么解决**：物品表加 `aliases` 字段（逗号分隔即可），`matchItem` 的第 2.5 级查别名表；
  或在新建物品时引导用户填 1~2 个常见叫法。**需要迁移，第四批次不做**。

### 5. 置信度标定的样本量不够（n=8）

`CONFIDENCE_THRESHOLD = 0.6` 现在是「**实测过、没发现不合适**」，不是「调出来的最优值」。
10 条样本里 2 条直接 `unrecognized`（没有分数），实际参与统计的只有 8 条；
中间那段无人区（0.5~0.85）很可能只是抽样巧合。

- **为什么现在不修**：这批样本够证伪「0.6 明显不合适」，不够支撑精细调参；
  为 8 个数据点去动一个数，等于用噪声指导决策，而且阈值提高的成本是「每次都要多点一次确认」。
- **将来怎么解决**：样本扩到 30 条以上（尤其要补中间地带的输入）再重跑标定脚本；
  同时用 `source = 'ai'` 的流水**撤销率**作为更真实的信号 —— 用户事后删掉的那条，说明当时不该让他一路确认到底。

### 6. 物品上下文有上限（200 件）

`prompt.ts` 里 `MAX_CONTEXT_ITEMS = 200`：物品再多就不进上下文了，模型看不到自然也抄不出名字。

- **为什么现在不修**：家庭物品量在几十件量级，200 是防「误把归档物品全塞进来」的护栏；
  超过之后多出来的物品对消歧的帮助趋近于 0，却要实打实付 token。
- **将来怎么解决**：如果真有增长到几百件的用户，先按「最近有流水的物品」排序再截断（比现在按列表顺序截更聪明），
  或者干脆做一次本地召回（BM25 / 模糊搜索 top-k）再喂给模型。

## 8. 决策记录

| # | 决策 | 理由 |
|---|---|---|
| 1 | 解析结果**必须用户确认**才能落库 | LLM 会出错，库存由流水求和，写错一条用户要翻历史对账 |
| 2 | 保留 `unknown` 作为唯一「看不懂」出口 | 没有它模型遇到无关输入会硬猜 |
| 3 | `action` 枚举保留 `discard` | 「扔了 / 过期丢掉」归成 consume 会让流水语义错，按类型统计查不到 |
| 4 | 单位换算**不属于** parse 层 | `normalizeUnit` 只做保守归一；换算依赖物品的 packSize，交给 `match.ts` |
| 5 | 「用完了」当前按 unknown 处理，接受 | 无上下文时确实识别不出物品，见下方待办 2 |
| 6 | 单位不一致用**轻量提示条**，不做阻断 | 单位不一致不是错误，只是「按基础单位记」；阻断会让用户每次多点一次。UI 显示「按「盒」记」，用户看一眼确认即可提交 |
| 7 | 兜底：quantity 为 null 时必须 needsReview | 已在 `parse.ts` 落地（`collectReviewReasons`），与 unit 无关，单条即触发 |
| 8 | AI 落的流水 `source = 'ai'` | `MovementSource` 新增 `'ai'`，四类动作（含 discard / adjust）一律带上。区分的是**录入方式**而非「谁负责」——有了它才能统计 AI 录入占比、以及回头评估 AI 记得准不准 |

## 待办

### 1. ✅ `match.ts`：LLM 单位与物品基础单位不一致 —— 已在第三批次落地

实测信号：「扔了一瓶过期牛奶」→ LLM 返回 `unit: "瓶"`，而物品「牛奶」的基础单位是**盒**。
数量 `1 瓶 ≠ 1 盒`，当时会静默通过。

**已实现**：`checkUnitMatch(aiUnit, item)` 返回 `same` / `converted` / `review` 三态，
`review` 表示对不上且无法换算，UI 必须让用户过一遍；换算系数由 `applyUnitFactor` 应用，
且**只在 `converted` 时才真的乘**。
现实约束：种子数据 `packSize = 1`，所以目前 `converted` 基本走不到，不一致大多落 `review`（见局限 3）。

> 真机验证（第五批次）：用户实际列表里没有「牛奶」，走的是 `none` 分支，所以当时看不到黄色单位提示条 ——
> 这是**符合设计**的 —— 没有物品就没有「基础单位」可比，`unitCheck` 从一开始就是 null。
> 该分支的前提与结论都由 `scripts/ai-parse-smoke.mjs` 分组 3 断言钉住。

### 2. 物品详情页进入 AI 输入框时带上当前物品（第四批次 UI 时定）

实测信号：「用完了」→ 返回 `unknown`。当前行为正确（句子里没有物品名，无东西可落库），
但产品上不友好。

**改进方向**：如果从物品详情页进入 AI 输入框，可带上当前物品作为上下文，
「用完了」就能识别成 **该物品 + consume + 数量未知**（走 needsReview 让用户补数量）。
是否做、怎么做，第四批次 UI 时再定。

### 3. 物品单位别名（长期，不早于第五批次）

根因：`match.ts` 的第 3 级是**字面子串**匹配，匹配不到**上位词/同义词**。
实测：「纸巾」匹配不到「手帕纸」（「手帕纸」里没有「纸巾」这俩字）→ 返回 none。
这类情况目前靠 prompt 规则 1 缓解（要求模型原样抄列表里的名字），但不彻底。

**要做**：物品支持单位/名称别名（物品表加 `aliases` 字段），或在新建物品时引导用户填常见别名。
**需要改数据模型 + 迁移**，第四批次不做（见局限 4）。

### 4. 「AI 录入占比」统计（第五批次或更晚）

`source = 'ai'` 已经落库，但**还没有任何页面用它**。
要做的是统计页加一个口径：按 `source` 分组数流水，得出「AI 记了多少条 / 占比多少」。
顺带可以对比 AI 录入与手写录入的**撤销率**（`deleteMovement` 的次数），
那是比置信度更真实的「AI 记得准不准」信号。

### 5. ✅ 置信度阈值调参 —— 已在第五批次完成：结论「保留 0.6」

10 条典型输入实测（详见 §5）：分布双峰且中间真空，0.6 / 0.7 / 0.8 判定完全一致，
只有 0.5 会漏掉「好像用了一些纸」。结合「降低阈值唯一能省下的一次点击，收益小于写错一条流水的代价」，
**保留 0.6**，并把实测数据与方法局限写进了 `CONFIDENCE_THRESHOLD` 的注释。
后续若要再动这个数，先把样本扩到 30 条以上重跑标定（见局限 5）。

## 已知限制

- API Key 放在客户端（`.env` 的 `EXPO_PUBLIC_DEEPSEEK_API_KEY`），`EXPO_PUBLIC_` 前缀的变量会被 Metro 内联进 bundle，
  拿到安装包的人可以解出来。**生产环境需要后端代理**。个人项目（额度小、可随时吊销）接受这个取舍，README 里写明。
- `deepseek-chat` 是服务端别名，实测响应里的 `model` 字段回的是 `deepseek-flash`。
  输出分布会随这次映射漂移，`DEFAULT_MODEL` 刻意保留成常量就是为了届时只改一个值。
